# 基线模型

> 每个 baseline 一节：一句话定位 → 原理 → 口径 → 数字 → 对照。
> 公共口径：`docs/benchmark_repro.md`（官方协议与官方数字）、`docs/eda.md`（切分后数据分布）。
> 评测在第一遍切分上做（train 截止 25,823,600，候选池 627,648）：val（4,627 个有目标的用户）用来选超参，test（4,599）用来报告。
> `coverage` 有**两种用户集合**（官方自己在模型之间就不一致）：`coverage(全用户)` 与 `coverage(有目标)`，两条都报；全用户那份与评测窗口无关（val / test 同值）。见「版本 B 口径」与 `architecture.md`。
> 官方 final test 数字用的是第二遍训练集（`val_size=0`），与本仓库切分不同，不能并排比。

## popularity

**一句话**：给所有用户推同一份"最近最热门"的歌单，完全不看用户是谁。它是"不学习"的参照点——任何个性化模型打不过它，就说明没学到东西。（`scripts/04_popularity.py`，约 3 秒跑完）

**打分：按新旧打折的计数**

```
score(i) = Σ_{t ∈ item i} 0.9 ** ((max_ts - t) / (3600 * hour))
```

- 每条 Listen+ 记录按距"现在"的时间打折，同一首歌的折扣值相加。
- `max_ts` = 训练集最大时间戳（模型眼里的"现在"）→ 只用训练期信息，不倒灌未来。
- `hour` 是衰减尺度：`hour=1` 表示每过 1 小时权重 ×0.9（24 小时前只剩 0.08）；`hour=24` 更扁平；`hour=0` 即纯计数、不打折。

**为什么要扫 `hour`**：热门会漂移（实测活动量 300 天里近翻倍、还有很强的日周期），`hour` 决定"往前看多久"。在 val 上扫官方那 7 档，最优 **hour=1.0** = "最近一两天听得最多的歌"最能预测次日，与数据非平稳是一致的。

**排序**：全局一份 top-100，不做 per-user 排除（官方口径）→ 人人相同；没有"听过就不再推"这回事，所以指标里含很重的**回访**成分。

## itemknn

**一句话**：把"用户最近听过什么"沿着共同听众铺到全站物品上——把物品表示成"哪些用户听过它"、把用户表示成历史物品的时间衰减加权和，做内积排序。第一个真正个性化、且明显超过 popularity 的基线。（`scripts/05_itemknn.py`，一档约 1 分 20 秒，13 档网格约 16 分钟）

**怎么算**（对齐官方 `models/itemknn/main.py`；代码级出处与实现取舍写在脚本 docstring 里）

设 `C` 为训练集的"用户 × 物品"计数矩阵（同一 (uid, item) 的多次交互相加）：

```
item_emb[i, v] = C[v, i] / ||C[v, :]||_2                       物品 = 用户频率向量，按该用户归一
W[u, i]        = Σ_{t ∈ (u, i)} 0.9 ** ((该用户最后一次 - t) / (3600 * hour))
A              = W @ C.T                                       用户表示
score(u, i)    = Σ_v A[u, v] * item_emb[i, v]                  取全局 top-100（不过滤已交互物品）
```

- `hour` 还是时间衰减尺度，含义与 popularity 一致；区别是这里的"现在"是**每个用户自己的最后一次交互**，popularity 用的是全局 `max_ts`。
- 官方接着还要把 `A` 按行做 L2 归一，我们**省掉了**：逐行除以一个正常数不改变该行的排序，而指标只看 top-k。
- 求和范围是坑：`A[u, v] = Σ_i W[u, i] · C[v, i]` 里的 `C[v, i]` 要对 C 的**整列**求和，`v` 不必落在 W 的支撑里（W 只是被官方的 `eliminate_zeros(1e-9)` 清掉了权重下溢的那些对——hour=0.5 时 895 万个对只剩 57 万个）。第一版写成"W 和 C 都限制在保留的对上"，靠与官方逐项对照才发现。
- `hour=0` 在这里**不是** popularity 那个"纯计数"：官方 `tau=0.0`，`0.0**0=1`、`0.0**正数=0`，于是只剩"每个用户最后一次事件"对应的那些对。

## sasrec

**一句话**：不再手工设计打分公式，而是用一个**因果自注意力 Transformer** 学"用户下一步会听什么"——把推荐当序列预测做。三个基线里唯一要训练、也是唯一带随机性的一个。（`scripts/06_sasrec.py`；seq 200 时 50 epoch 329.8 秒，seq 512 的耗时见下）

**怎么算**（对齐官方 `models/sasrec/`）

```
用户历史（item id，截到最后 MAX_SEQ_LEN 条；本机 512）
  → item embedding + 位置 embedding（倒序编号：最新行为是位置 0）
  → LayerNorm → Dropout → LAYERS 层自写 block（因果掩码 + padding 掩码；与 `nn.TransformerEncoderLayer` 同构，
    自己拼是为了能往注意力分数上加**加性偏置**——那头只吃布尔 mask）
  → 取最后一格的向量当用户表示
训练：每个位置预测"下一首"，每位置随机 1 个负样本，BCEWithLogits([正分; 负分], [1; 0])
评测：用户向量 × 全部物品 embedding 内积 → top-100（不过滤已交互物品）
```

- 训练样本就是 `item = seq[:-1]` / `positive = seq[1:]`（`data.py::TrainDataset`），负样本每个位置 1 个。
- 超参照官方默认：emb 128（官方 64）/ heads 2 / layers 4（官方 2）/ dropout 0.0 / lr 1e-3 / Adam / batch 256 / seed 42；epoch 官方默认 100，我们取 50（与 `docs/benchmark_repro.md` 记录的本机设置一致）。**偏离官方默认的有三处**：序列长度 512（官方 200，见「序列长度 200 → 512」）、emb 128 与层数 4（见「容量包」）。也就是说现在这份 sasrec 已经不是“官方复现”配置，对表能力由口径 B + 文档记录保留。
- 没有 `hour` 这类超参，所以没有网格扫描；但**训练本身有随机性**（初始化、负采样、shuffle），数字不可逐位复现。
- 设备：训练 MPS、推理 CPU（官方在 MPS 上跑 eval 会崩），**且推理按用户分批**（`INFER_BATCH = 512`）——注意力矩阵是 `(B, heads, L, L)`，L=512 时全量喂 9,207 个用户要约 19 GB，实测会疯狂换页（swap 吃掉 18 GB、跑了 4 分半没结束，只能停掉）；分批后一个窗口 32 秒（同一份 checkpoint 换 `INFER_BATCH = 2048` 重算，**指标逐项相同**）。
- **耗时（seq 512）**：脚本自报每 epoch 12.7–15.4 秒、50 个之和 686.5 秒（11.4 分钟）；那一次的墙钟是 **30.8 分钟**，差额已查明——**机器在训练期间（电池供电）反复 Idle Sleep**（`pmset` 日志：16:33:59→16:50:23 一次睡了 16.4 分钟，16–17 点共 8 次、合计约 19.6 分钟），而 `time.perf_counter`（mach_absolute_time）**不计休眠时间**，所以 epoch 计时 = 纯计算、墙钟 = 含休眠（同一现象在 `docs/benchmark_repro.md` 的“本机偏差”里也记过一次）。**估成本要用 epoch 计时**；口径 B 那次没碰到休眠，自报 793.8 秒 = 墙钟 13.2 分钟，两者吻合。seq 200 时自报 4.9 → 7.0 秒/epoch、总 329.8 秒。

**评测实现里一个缺陷：padding 行的 NaN（2026-09-21 在第 1 步重构时查出）**

**先说结论：这一节里 2026-09-21 之前跑出的所有 sasrec 数字都被下面这个缺陷压低，已作废。**

- **现象**：旧实现（`nn.TransformerEncoder` + 布尔 `attn_mask` + 布尔 `src_key_padding_mask` + `need_weights=False`）
  在 **eval** 下走 MHA 的 fused fast path，而那条路径对“整行都被 mask 掉的 padding 行”返回 **NaN**（没做 `nan_to_num`）。
- **怎么变成评测问题的**：左填充下，一个 padding 行在因果 + padding 掩码下确实没有任何可见 key；它的 NaN 在第 2 层
  当 K/V 使用，把**有效行**的输出也污染成 NaN。
- **为什么之前没被发现**：`train` 模式不走 fast path（所以 **训练完全正常**，loss 一路正常下降），而当时那次“官方前向逐位一致”
  的对照是在**满长度（无 padding）序列**上做的——没有 padding 行，自然没有 NaN。
- **影响面（实测）**：9,207 个用户里 **2,321 个（25.2%）**——恰好是训练历史 < 512 的所有用户——用户向量为 NaN，
  它们的 top-100 变成垃圾（覆盖不到目标），recall 近似 0。文档里 sasrec 的 d64/512、d256、seq 200、口径 B 全部数字，
  以及用到 sasrec top-100 的 RRF 融合，都建立在这个缺陷上。popularity / itemknn 与 `rec_eval` 不走 transformer，**不受影响**。
- **修正后（同一份 checkpoint，同一份评测）**：

| 口径 A，d64 / seq 512 / 2 层 | 旧（NaN 污染） | 修正后 | 变化 |
|---|---|---|---|
| val recall@100 | 0.082480 | **0.100252** | +21.5% |
| val dcg@100 | 0.535689 | 0.594364 | +11.0% |
| val 回访 / 新歌 recall@100 | 0.103669 / 0.030482 | **0.124280 / 0.041743** | — |
| test recall@100 | 0.074404 | **0.090524** | +21.7% |
| test 回访 / 新歌 recall@100 | 0.094903 / 0.027782 | **0.113119 / 0.038047** | — |
| test coverage@100（有目标） | 0.024651 | 0.025481 | +3.4% |
| 口径 B test recall@100 | 0.076916 | **0.094515** | +22.9% |

- **现在防它的方式**（不只是“换了个写法碰巧没事”）：掩码折成一个**加性浮点矩阵**（未来位与 padding 位填 `-inf`），
  再给 padding 行留一个可见位（它自己的对角线）——**结构上就不存在“整行被 mask”**，softmax 恒良定义。
  这条不变式写进了 `SASREC.forward` 的注释里。
- 新实现已用同权重逐层对照验证与原实现等价：完整 block0（含 FFN、含按 head 的偏置）最大差 **4.8e-7**，
  MHA 返回的注意力权重差 **3e-8**；参数完全一致（同一份 checkpoint 两个实现都能装）。

**序列长度 200 → 512（第一项改进，2026-09-21）**

> 注意：这一节（与下面的「扩容」）的数字都是在上面那个 NaN 缺陷下测的，两边污染比例还不一样
> （< 200 的用户比 < 512 的少）。**只保留方向性结论，具体数字已作废**；修正后的证据看「容量包」一节。

动机：训练集历史长度（去重物品）中位 666 / p90 2,239（`docs/eda.md`），而官方默认的 `MAX_SEQ_LEN=200` 一直在被顶满——

**时间特征 Δ：试过一次，变差（2026-09-21）**

动机：sasrec **完全看不到时间**（`timestamp` 只用来排序），而 itemknn 的权重是 `0.9 ** (该用户最后一次 − 该次时间)`——
它恰好在回访轴（占 66.6%）上压着我们，所以先加一个最便宜的对应物。

做法：`Δ = 距该用户窗口内最后一次事件多久`（秒），对数分桶（5s / 15s / 1min / … / 90 天，13 桶），查一张
`(13 × EMB)` 的表加到 item / 位置 embedding 上。训练与推理的查询位置都恰好是 Δ = 0（训练时参照取**输入序列**的
最后一次事件），口径一致、不泄露未来。**只改这一处**（EMB 回到 64 以便快迭代）。

|---|---|---|---|
| recall@10 | 0.046167 | 0.044196 | −4.3% |
| recall@100 | 0.082480 | 0.077826 | **−5.6%** |
| 命中率@100 | 0.579425 | 0.563648 | −2.7% |
| dcg@100 | 0.535689 | 0.506480 | −5.5% |

- **全指标同向变差**，训练 loss 也更差（epoch 50：0.0486 vs 0.0471）→ 既不是过拟合，也不是“记住了轨迹”；
  这条特征没带来可用信号，反而干扰了注意力。
- 连**回访轴也没帮上**（−6.5%）——与“itemknn 靠 Δ 取胜、所以 Δ 有用”的直觉相反。可能的解释（**推断，未验证**）：
  位置 embedding 已经隐含了“多久以前”的序信息（本数据里序与时间高度相关），而逐位置的 Δ 是**绝对分桶**、
  不随 query 变；模型要的可能是“某个历史事件相对**现在**多远”的**成对**信号（下一个候选就是相对时间偏置）。
- 成本：15.0 秒/epoch（与不加 Δ 时同量级），50 epoch + val 推理共 804 秒 ≈ 13.4 分钟。
- 代码留了开关 `USE_TIME_FEATURE`（默认 **False**，回到已知更好的配置）；要复现这版改成 True 重跑。
  权重没丢：`artifacts/sasrec/state_l512_d64_delta.pt` 就是这版 d64+Δ（无 Δ 的备份在 `state_l512_d64.pt`）。

  embedding 盖住了——而是“两个历史事件之间隔了多久”的**成对**信号，所以下一个候选就是相对时间偏置（见下一节）。

**相对时间偏置 b[Δt桶]：试过一次，变差（2026-09-21）**

动机：把上一条的推断坐实。出处是参考书里 HSTU 那一支——`bias_{i,j} = f(p_i − p_j, t_i − t_j, type)`
（`reference/fun-rec/docs/_sources/chapter_6_scaling/1.hstu.rst.txt` 的“相对位置编码的重新设计”），
以及 `2.gen_rank.rst.txt` 那一节“位置与时间：该学习什么、该编码什么”（HSTU 的可学 RAB 是 O(N²) 访存瓶颈，
GenRank 的替代是“绝对信息用 O(N) embedding、相对信息用简单 bias”）。

做法（**只改这一处**，位置侧完全不动）：

- 把可学的 `b[Δt 桶]`（按 head 分开）**加到注意力分数上**（`score = QKᵀ/√d + b`，不是取代点积）。
- `Δt = t_i − t_j`，**参照点是查询位自身**（训练位置 i 预测 i+1，用的全是 i 时刻已知的时间；推理只读最后一格）——
  因果下 Δt 恒 ≥ 0，不需要参考实现那个 `abs`。
- 桶边界沿用本机 `TIME_BOUNDS` 的 13 个对数桶；Δt 桶索引每 batch 算一次、所有层共用（否则就是参考书里讲的 O(N²) 访存瓶颈×层数）。
- 偏置表**初始化为 0**：第一轮的行为就是 b ≡ 0 那版，便于对照。

**参考实现有两处不能照抄**（已查）：`fun-rec` 的 `config_hstu.py` 里 `attention_type` 默认是 `dot_product`
——时间偏置在参考实现里**默认没开、也没调过**；它把**原始秒**时间戳用 `max_interval=1024` 截断后建表
（17 分钟以上的间隔全部并成一档，而我们数据里 >30 分钟的占 7.7%）。另外它默认分支是 `outputs = attention_bias`，
即**用 bias 取代点积**；我们要的是相加。

开工前的三项检查（都先做了再跑）：Δt 桶占用（前 64 个用户、6,646,277 对，**13 个桶都有实质样本**：
0.8/0.5/0.2/0.3/1.6/2.6/2.9/7.0/11.9/16.4/28.3/23.3/4.0%）；Δt 与旧 Δ 预分桶**逐位等价**（有效位最大差 0）；
完整 block0 与手工复算差 **4.8e-7**、两个 head 的偏置对调会真的改变输出（1.0e-2，说明 head 维没写串）。

> **已作废，待重做。** 这张表的 sasrec 用的是 d256 那版的 top-100，而那份数字是在 NaN 缺陷下算出来的
> （sasrec 用户向量有 25% 是 NaN）——融合的输入本身就是错的。现在 sasrec 单模型已经是 0.1108（test）、
> 而且两条轴都领先，“融合能不能再赚”这个问题要重新问一次。

拿各模型的 top-500 做 RRF（K0=60）再取 top-100，指标同上（口径 A test，逐用户）。**sasrec 用 d256 那版**（数字受缺陷污染，见上框）：

| 方法 | 全部 recall@100 | 回访 | 新歌 |
|---|---|---|---|
| itemknn | 0.0981 | 0.1272 | 0.0246 |
| sasrec-512/d256 | 0.0800 | 0.1022 | 0.0308 |
| **itemknn + sasrec** | **0.1081** | **0.1429** | 0.0285 |
| itemknn + sasrec（sasrec ×2） | 0.0978 | 0.1273 | 0.0302 |
| itemknn + sasrec + popularity | 0.1018 | 0.1264 | **0.0444** |

- **融合明显超过 itemknn：0.1081 vs 0.0981（+10.2%）**，也超过两个单模型——两者信息确实互补。
  而且 d256 之后融合的增益变大了（d64 时是 0.1014，+3.4%）：**单模型变强，融合也跟着变强**。
- 但**强项仍然重叠在回访轴**：融合的回访 0.1429 比 itemknn 单独（0.1272）高 12%，而新歌 0.0285 反而**低于** sasrec 单独的 0.0308。
- 给 sasrec 加倍权重变差（0.0978，几乎回到 itemknn 单模型）：回访轴由 itemknn 主导。
- 三路融合（加 popularity）新歌 **0.0444**（≈ popularity 单独的 0.0448），代价是“全部”掉到 0.1018——仍高于 itemknn。
- 这是**一次性核对**（未固化成脚本）；同一进程里重算的三个单模型数字与主表逐项一致（0.0981 / 0.0800 / 0.0470），
  所以融合增益不是口径差异带来的。

**与官方实现的一致性核对**

- **前向逐位一致**：把官方那份 50-epoch checkpoint 的权重导进来（词汇表 = 631,003 个物品 + 1 行 padding），取 200 条长度正好 200 的序列，用我们的实现在同一批 id 上前向 → 最大绝对差 **0.000e+00**。这一步覆盖 item/位置 embedding、LayerNorm、因果掩码 + padding 掩码、取最后一格。
- **训练侧只能对量级**：初始化、负采样、shuffle 都有随机性，逐位对不了。coverage@100（有目标用户）我们 **0.025056**（修正评测后的 d64/512）vs 官方 0.015887——两边都是“只算有目标的用户”这个口径，但数值差 58%：这一格本来就跟模型强度走，而我们的 sasrec 已经不是官方配置（seq 512），**不能当作一致性证据**（popularity / itemknn 那两格才是，它们是同配置重实现）。
- **2026-09-21 重写注意力 block 之后**，上面这条“前向逐位一致”仍然成立：新 block 与旧实现逐层等价（完整 block0 最大差 4.8e-7、MHA 注意力权重差 3e-8），而旧实现与官方逐位一致（那条对照本来就是在无 padding 的满长度序列上做的）。
- **三处已知差异**（写在脚本 docstring）：① padding 用 id 627,648 且排序时排除（官方用 0，且把 padding 行也当候选）→ 我们的候选池 627,648，与另两个基线一致；② 位置编号固定按左填充到 MAX_SEQ_LEN（官方随 batch 内最大长度平移，而 eval 的 DataLoader 还 `shuffle=True`，同一个用户换 batch 结果会变）；③ 切分：官方在第二遍训练集上训练并报 test；我们在第一遍 train 上训练，val 选超参、test 报告。**注意“前向逐位一致”那条只在 seq 200 下成立**（官方 checkpoint 的位置 embedding 就是 200 行）。

**量级**（官方 test 表，recall@100）：random 0.00006 → popularity 0.0479 → **sasrec 0.0828** → itemknn 0.1085。

B = `val_size=0`：train 截止 25,911,800（val 窗口并回训练集，比 A 多 **145,044 行** Listen+）、**没有 val**；id 空间 **用户 9,208 / 候选池 629,298**，与官方 `random_rec` 打印的 `NUM_USERS 9208, NUM_ITEMS 629298` 逐个相同。test 窗口仍是 4,599 个有目标的用户 / 157,695 行，但目标里“训练集没出现过（`-1`）”的行从 A 的 2,332 降到 **1,956**（B 的训练集多覆盖 1,650 个物品）。

官方只报一个 coverage：popularity / itemknn 是**全用户**口径、sasrec 是**有目标用户**口径（加粗的就是官方那一格）。

- **popularity 六位小数全中**（recall / dcg / 命中率 / coverage 全部指标都同）——切分、id 空间、候选池、评测实现这一层已经钉死。
- **itemknn 差 ≤ 5.3e-5**（recall@100 0.108529 vs 0.108476），`命中率@100` 完全相同。残差是 float32 求和顺序与并列取舍（`05_itemknn.py` docstring 的“已知差异”）。
- **sasrec 比官方高 14.1%**（recall@100 0.094515 vs 0.082849）——这个方向跟修正评测前（当时是“低 7.2%”）反了。
  **原因是我们这份不是官方配置**：序列长度 512（官方 200）是这里最大的差异，另有两处已记差异——
  词表（我们 `n_items+1 = 629,299`，官方 = 全部 Listen+ 物品 + padding 行 = 631,004）与位置编号（我们固定左填充到
  `MAX_SEQ_LEN`，官方按 batch 内最大长度平移）。**所以这一格只能说明“同一套切分/id 空间/候选池/评测代码下能跑赢官方已发表的数”，
  不能算“复现一致”**（口碑一致的是 popularity 与 itemknn 那两格）。单 seed 42 的随机性也在。
- 口径 B 的 sasrec 是 **d64 / seq 512 / 2 层**那版（`state_b.pt`）；口径 B 的**容量包还没跑**。

**coverage：两种用户集合都报**（官方自己不一致）

- 官方的 `Coverage` 是 `cut_off_ranked=False`（`yambda/evaluation/metrics.py:185`）——**不裁到“有目标的用户”**；`popularity` / `itemknn` 的 `Ranked` 用训练集里的**全部**用户（`popularity/main.py:130` 的 `train.select("uid").unique()`）。
- 但官方 **sasrec** 的 `eval.py:91` 有一句 `train_df.join(eval_df, on='uid', how='inner')`，只把“训练 + 测试都出现”的用户送进 `Ranked`。**官方自己的 coverage 定义在模型之间就不一致。**
- 所以 `scripts/rec_eval.py` 两条都报：`coverage(全用户)`（对 popularity / itemknn）与 `coverage(有目标)`（对 sasrec）。**popularity / itemknn 两条都能对上官方那一格**（itemknn B 全用户 0.064991 vs 官方 0.064990，差 1e-6）；sasrec 那格两边口径相同但数值差 58%（我们的 sasrec 不是官方配置，见上）。
- `coverage(全用户)` 与评测窗口无关（top-k 只由训练集和模型决定），所以同一口径下 val / test 同值——上表每行只有一个数。
- 量级参考（B 口径）：itemknn 全用户 = 40,899 个物品、有目标 = 24,241 个；两条的差别完全由用户集合解释（4,599 vs 9,208 个用户）。
