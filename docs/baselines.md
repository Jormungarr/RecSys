# 基线模型

> 每个 baseline 一节：一句话定位 → 原理 → 口径 → 数字 → 对照。
> 公共口径：`docs/benchmark_repro.md`（官方协议与官方数字）、`docs/eda.md`（切分后数据分布）。
> 当前评测在 val 上（第一遍切分：train 截止 25,823,600，候选池 627,648）；官方 final test 数字用的是第二遍训练集（`val_size=0`），本仓库还没产出。

## popularity

**一句话**：给所有用户推同一份"最近最热门"的歌单，完全不看用户是谁。它是"不学习"的参照点——任何个性化模型打不过它，就说明没学到东西。（`scripts/04_popularity.py`，约 3 秒跑完）

**打分：按新旧打折的计数**

```
score(i) = Σ_{t ∈ item i} 0.9 ** ((max_ts - t) / (3600 * hour))
```

- 每条 Listen+ 记录按距"现在"的时间打折，同一首歌的折扣值相加。
- `max_ts` = 训练集最大时间戳（模型眼里的"现在"）→ 只用训练期信息，不倒灌未来。
- `hour` 是衰减尺度：`hour=1` 表示每过 1 小时权重 ×0.9（24 小时前只剩 0.08）；`hour=24` 更扁平；`hour=0` 即纯计数、不打折。

**为什么要扫 `hour`**：热门会漂移（实测活动量 300 天里近翻倍、还有很强的日周期），`hour` 决定"往前看多久"。在 val 上扫官方那 7 档，最优 **hour=1.0** = "最近一两天听得最多的歌"最能预测次日，与数据非平稳是一致的。

**排序**：全局一份 top-100，不做 per-user 排除（官方口径）→ 人人相同；没有"听过就不再推"这回事，所以指标里含很重的**回访**成分。

**val 数字**（hour=1.0，4,627 个有目标的用户，候选池 627,648）

| 指标 | @10 | @50 | @100 |
|---|---|---|---|
| recall | 0.022164 | 0.032730 | 0.047727 |
| dcg | 0.097404 | 0.198800 | 0.266662 |
| 命中率（官方 `ndcg`） | 0.129025 | 0.308623 | 0.408472 |
| coverage | 0.000016 | 0.000080 | 0.000159 |

- recall@100 = 4.77%：用户次日的听歌记录里，约 4.8% 落在全局 top-100 里；
- 命中率@100 = 40.8%：约四成用户至少命中一次（这是官方那个有 bug 的 `ndcg@100` 的真实含义）；
- coverage@100 = 100 / 627,648 ≈ 0.016%：榜单只有 100 个位置，全站只覆盖 100 首歌——结构性缺点。

评测定义与官方口径的对应关系（recall 分母 = 目标行数、dcg 定义、官方 ndcg 等价于命中率）写在 `scripts/04_popularity.py` 的 docstring 里。

**量级**（官方 test 表，recall@100）：random 0.00006 → **popularity 0.0479** → sasrec 0.0828 → itemknn 0.1085（≈ popularity 的 2.3 倍）。有信号，但不个性化，天花板低。

**两个对照**（同一次运行输出）

| 口径 | 用户数 | recall@100 | 命中率@100 |
|---|---|---|---|
| 官方口径（不过滤、保留不可排名的 -1 目标） | 4,627 | 0.047727 | 0.408472 |
| 过滤已交互物品（候选 + 目标都去掉历史） | 3,453 | 0.055647 | 0.247611 |
| 只看可排名目标（丢掉 -1 行） | 4,611 | 0.048248 | 0.409889 |

- 过滤已交互后：命中率从 40.8% 掉到 24.8%，且 4,627 个用户里只剩 **3,453** 个还有"新歌"目标 → popularity 的命中很大一部分是"推的歌用户本来就反复听"，在"帮用户发现新歌"上比看起来弱得多。
- `-1`（训练集没出现过的物品）的影响：recall@100 相对 +1.1%——真实存在，但很小。

**为什么值得存在**：① 给后面的模型定地板；② 当评测管线的**回归测试**（我们的实现与官方逐项一致到 6 位小数，7 档 hour 全中，最优 hour 也都是 1.0）；③ 3 秒跑完，口径改动随时重跑核对。

## itemknn

**一句话**：把"用户最近听过什么"沿着共同听众铺到全站物品上——把物品表示成"哪些用户听过它"、把用户表示成历史物品的时间衰减加权和，做内积排序。第一个真正个性化、且明显超过 popularity 的基线。（`scripts/05_itemknn.py`，一档约 1 分 20 秒，13 档网格约 16 分钟）

**怎么算**（对齐官方 `models/itemknn/main.py`；代码级出处与实现取舍写在脚本 docstring 里）

设 `C` 为训练集的"用户 × 物品"计数矩阵（同一 (uid, item) 的多次交互相加）：

```
item_emb[i, v] = C[v, i] / ||C[v, :]||_2                       物品 = 用户频率向量，按该用户归一
W[u, i]        = Σ_{t ∈ (u, i)} 0.9 ** ((该用户最后一次 - t) / (3600 * hour))
A              = W @ C.T                                       用户表示
score(u, i)    = Σ_v A[u, v] * item_emb[i, v]                  取全局 top-100（不过滤已交互物品）
```

- `hour` 还是时间衰减尺度，含义与 popularity 一致；区别是这里的"现在"是**每个用户自己的最后一次交互**，popularity 用的是全局 `max_ts`。
- 官方接着还要把 `A` 按行做 L2 归一，我们**省掉了**：逐行除以一个正常数不改变该行的排序，而指标只看 top-k。
- 求和范围是坑：`A[u, v] = Σ_i W[u, i] · C[v, i]` 里的 `C[v, i]` 要对 C 的**整列**求和，`v` 不必落在 W 的支撑里（W 只是被官方的 `eliminate_zeros(1e-9)` 清掉了权重下溢的那些对——hour=0.5 时 895 万个对只剩 57 万个）。第一版写成"W 和 C 都限制在保留的对上"，靠与官方逐项对照才发现。
- `hour=0` 在这里**不是** popularity 那个"纯计数"：官方 `tau=0.0`，`0.0**0=1`、`0.0**正数=0`，于是只剩"每个用户最后一次事件"对应的那些对。

**hour 网格**（官方 13 档，与 popularity 同一选法：按命中率@100 选）

| hour | 0 | 0.001 | 0.002 | 0.004 | 0.008 | 0.016 | 0.032 | 0.064 | 0.128 | 0.256 | **0.5** | 1.0 | 2.0 |
|---|---|---|---|---|---|---|---|---|---|---|---|---|---|
| 命中率@100 | 0.5850 | 0.5879 | 0.5917 | 0.5941 | 0.5954 | 0.5943 | 0.6006 | 0.6036 | 0.6010 | 0.6019 | **0.6038** | 0.5987 | 0.5870 |

- 曲线很平：13 档全落在 0.585 ~ 0.604，随便挑一档都远高于 popularity——说明这个模型对衰减尺度不敏感。
- 最优 **hour=0.5**，**与官方在 val 上选出的 `best_hour=0.5` 一致**（官方 `itemknn` 在 test 表上也报 0.5）。
- 但 `recall@100` 的最大值在 hour=0.064（0.104467），比 hour=0.5（0.103341）高 1.1%：官方用那个有 bug 的 `ndcg`（= 命中率）当验证指标，选出的 hour 与按 recall 选的不一样。差距很小，但说明**选参指标本身会影响结论**。为什么命中率偏好更长的记忆、recall 偏好更短的，**未解释**。

**val 数字**（hour=0.5，4,627 个有目标的用户，候选池 627,648）

| 指标 | @10 | @50 | @100 |
|---|---|---|---|
| recall | 0.057684 | 0.077010 | 0.103341 |

**与 popularity 对比**（同一切分、同一份评测，hour 各自最优）

| 指标 | popularity | itemknn | 倍数 |
|---|---|---|---|
| recall@100 | 0.047727 | 0.103341 | 2.2× |
| 命中率@100 | 0.408472 | 0.603847 | 1.5× |
| coverage@100 | 0.000159 | 0.037583 | 236× |

- coverage@100 从"全站只推 100 首歌"变成覆盖约 **2.36 万首**（0.037583 × 627,648）——个性化确实起来了，不再是人人都一样。
- 但注意两家都没过滤已交互物品，命中的"回访"成分仍然很重（popularity 那份对照显示去掉历史后命中率从 40.8% 掉到 24.8%）。

**与官方实现的一致性核对**（本机，同一份第一遍切分，hour=0.5）

在 vendor 的独立 env 里用官方代码（`rank_items`，batch=128）算了一遍 top-100，与我们逐个用户比：

- 平均重合 **99.88/100**，4,627 个用户里 **4,587 个完全一致**；top-10 平均重合 9.99/10。
- 中间量也对上了：`A` 的元素和 237,413,104 vs 官方 237,413,088（相对差 7e-8），`A` 前 5 行最大绝对差 3e-5。
- 残余差异只来自 float32 的求和顺序，以及并列项的取舍（官方 `torch.topk` 对并列的取舍未定义；我们固定按 item id 升序）。两边都写在脚本 docstring 的"已知差异"里。
- 指标：同一份 top-100 喂进同一份评测，命中率@100 我们 0.603847 / 官方 0.603631，recall@100 0.103341 / 0.103335。

**量级**（官方 test 表，recall@100）：random 0.00006 → popularity 0.0479 → sasrec 0.0828 → **itemknn 0.1085**。我们 val 上是 0.1033，同量级；但切分不同（第一遍 vs 第二遍），**不能直接比**。

## sasrec

**一句话**：不再手工设计打分公式，而是用一个**因果自注意力 Transformer** 学"用户下一步会听什么"——把推荐当序列预测做。三个基线里唯一要训练、也是唯一带随机性的一个。（`scripts/06_sasrec.py`，50 epoch 总耗时 329.8 秒）

**怎么算**（对齐官方 `models/sasrec/`）

```
用户历史（item id，截到最后 200 条）
  → item embedding + 位置 embedding（倒序编号：最新行为是位置 0）
  → LayerNorm → Dropout → 2 层 TransformerEncoder（因果掩码 + padding 掩码）
  → 取最后一格的向量当用户表示
训练：每个位置预测"下一首"，每位置随机 1 个负样本，BCEWithLogits([正分; 负分], [1; 0])
评测：用户向量 × 全部物品 embedding 内积 → top-100（不过滤已交互物品）
```

- 训练样本就是 `item = seq[:-1]` / `positive = seq[1:]`（`data.py::TrainDataset`），负样本每个位置 1 个。
- 超参照官方默认：emb 64 / heads 2 / layers 2 / dropout 0.0 / lr 1e-3 / Adam / batch 256 / seq 200 / seed 42；epoch 官方默认 100，我们取 50（与 `docs/benchmark_repro.md` 记录的本机设置一致）。
- 没有 `hour` 这类超参，所以没有网格扫描；但**训练本身有随机性**（初始化、负采样、shuffle），数字不可逐位复现。
- 设备：训练 MPS、推理 CPU（官方在 MPS 上跑 eval 会崩）。每 epoch 从 4.9 秒涨到后段 ~7.0 秒，**未解释**。

**val 数字**（50 epoch；4,627 个有目标的用户，候选池 627,648）

| 指标 | @10 | @50 | @100 |
|---|---|---|---|
| recall | 0.042965 | 0.052490 | 0.074572 |
| dcg | 0.212808 | 0.364183 | 0.469016 |
| 命中率（官方 `ndcg`） | 0.257834 | 0.456235 | 0.559326 |
| ndcg（正确） | 0.052148 | 0.053024 | 0.062667 |
| coverage | 0.006841 | 0.012494 | 0.016782 |

**三个基线并排**（同一切分、同一份评测）

| 指标 | popularity | sasrec | itemknn |
|---|---|---|---|
| recall@10 | 0.022164 | 0.042965 | 0.057684 |
| recall@100 | 0.047727 | 0.074572 | 0.103341 |
| 命中率@100 | 0.408472 | 0.559326 | 0.603847 |
| coverage@100 | 0.000159 | 0.016782 | 0.037583 |

**与官方实现的一致性核对**

- **前向逐位一致**：把官方那份 50-epoch checkpoint 的权重导进来（词汇表 = 631,003 个物品 + 1 行 padding），取 200 条长度正好 200 的序列，用我们的实现在同一批 id 上前向 → 最大绝对差 **0.000e+00**。这一步覆盖 item/位置 embedding、LayerNorm、因果掩码 + padding 掩码、取最后一格。
- **训练侧只能对量级**：初始化、负采样、shuffle 都有随机性，逐位对不了。可用的是相对序——官方 test 表 itemknn 0.1085 > sasrec 0.0828 > popularity 0.0479，我们 val 上 0.1033 > 0.0746 > 0.0477，**序一致**；各自略低（第一遍训练集比第二遍短一天，评测集也不同，不能直接比）。coverage@100 我们 0.016782 vs 官方 0.015887。
- **三处已知差异**（写在脚本 docstring）：① padding 用 id 627,648 且排序时排除（官方用 0，且把 padding 行也当候选）→ 我们的候选池 627,648，与另两个基线一致；② 位置编号固定按左填充到 200（官方随 batch 内最大长度平移，而 eval 的 DataLoader 还 `shuffle=True`，同一个用户换 batch 结果会变）；③ 切分：官方在第二遍训练集上训练并报 test，我们在第一遍 train / val。

**量级**（官方 test 表，recall@100）：random 0.00006 → popularity 0.0479 → **sasrec 0.0828** → itemknn 0.1085。
